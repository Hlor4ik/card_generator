# AI-помощник для подготовки товарных описаний (КИП)

Прототип сервиса, который по структурированным данным о контрольно-измерительном
приборе формирует **черновик карточки товара** для B2B-интернет-магазина: SEO-заголовок,
SEO-описание, список характеристик, поисковые запросы и блок для менеджера.

Ключевой принцип — **никаких выдуманных характеристик**: все технические значения берутся
только из входных данных, а недостающие поля явно помечаются как «данных нет».

## Возможности

- Вход — JSON (файл, stdin или JSON API) либо простая веб-форма.
- Выход — Markdown, текст или JSON (удобно копировать контент-менеджеру).
- Для каждого товара формируется:
  - SEO-заголовок (≤ 70 символов);
  - SEO-описание (целевой объём 800–1200 символов);
  - структурированный список характеристик;
  - 3–5 поисковых запросов;
  - commercial-блок: кому подходит прибор и какие задачи решает.
- Обработка ошибок API, пустых полей и некорректного JSON.
- Предупреждения контент-менеджеру о нехватке данных и о числах, которых нет во входе.

## Установка

Нужен Python 3.10+.

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env   # и впишите ключ в OPENAI_API_KEY
```

### Конфигурация (`.env`)

API-ключ **не хранится в коде** — только в `.env` (он в `.gitignore`).

| Переменная         | Назначение                          | По умолчанию                  |
|--------------------|-------------------------------------|-------------------------------|
| `OPENAI_API_KEY`   | Ключ LLM (обязательно)              | —                             |
| `OPENAI_BASE_URL`  | Базовый URL OpenAI-совместимого API | `https://api.openai.com/v1`   |
| `MODEL`            | Модель                              | `gpt-6-luna`                  |

## Запуск

### CLI

```bash
# один или несколько файлов, формат md|json|text
python -m app.cli samples/product1.json samples/product2.json --format md

# из stdin
cat samples/product1.json | python -m app.cli - --format json

# сохранить результаты в каталог
python -m app.cli samples/*.json --format md --out examples
```

### Веб-форма и JSON API

```bash
uvicorn app.web:app --port 8000
```

- `GET  /` — HTML-форма: вставить JSON → получить карточку.
- `POST /generate` — JSON на входе и выходе (для интеграций):

```bash
curl -X POST http://127.0.0.1:8000/generate \
  -H 'Content-Type: application/json' \
  --data-binary @samples/product1.json
```

## Как устроено (ключевые решения)

### Защита от выдуманных характеристик — три рубежа

1. **Детерминированный список характеристик.** Блок «Характеристики» собирается
   **в коде напрямую из входных `specs`**, без участия LLM
   (`generator._characteristics_from_input`). Числа и единицы в этом блоке не могут
   быть искажены или выдуманы.
2. **Жёсткий системный промпт** (`app/prompt.py`): модель получает входные данные как
   единственный источник фактов и прямой запрет придумывать значения, стандарты,
   резьбы, классы точности, IP и т.п. Отсутствующие характеристики не упоминаются.
3. **Эвристическая пост-проверка** (`app/factcheck.py`): из сгенерированного текста
   извлекаются числа с единицами измерения (МПа, мА, мм, °C, резьбы G1/2, IP65 …) и
   сверяются со входом. Если встретилось значение, которого нет в данных, карточка
   получает предупреждение «проверьте вручную».

### Обработка неполных данных

- `name` обязателен; его отсутствие — ошибка валидации.
- Нет `manufacturer` / `specs` / `description` — не ошибка: в карточку подставляется
  «данных нет», а в блок «Требует внимания» добавляется предупреждение
  (`app/validation.py`).

### Устойчивость

- Ответ LLM запрашивается в JSON-режиме и валидируется; при нарушении лимитов
  (длина заголовка/описания, число запросов) выполняется **одна корректирующая
  попытка** с обратной связью, затем — мягкая подрезка и предупреждение
  (`app/generator.py`).
- Ошибки API (авторизация, лимиты, таймаут, сеть) перехватываются и показываются
  понятным текстом (`app/llm.py`).
- Учтены причуды семейства `gpt-6-luna`: вместо `max_tokens` используются
  `max_completion_tokens` и `reasoning_effort` (`app/config.py`, `app/llm.py`).

### Структура проекта

```
app/
  config.py       настройки из окружения (.env), секреты не в коде
  schema.py       Pydantic-модели входа и карточки
  validation.py   разбор/валидация входа, анализ полноты данных
  prompt.py       системный и пользовательский промпты
  llm.py          клиент OpenAI-совместимого API + обработка ошибок
  factcheck.py    эвристическая проверка на выдуманные числа
  generator.py    оркестрация: вход → проверки → LLM → карточка
  render.py       рендер в Markdown / текст / JSON
  cli.py          CLI
  web.py          FastAPI: форма + JSON API
samples/          два входных товара (второй — неполный)
examples/         готовые карточки для этих товаров
```

## Описание промпта

- **Системный промпт** задаёт роль (ассистент контент-менеджера магазина КИП),
  шесть «железных правил» фактологичности и строгую JSON-схему ответа
  (`seo_title`, `seo_description`, `search_queries`, `commercial_block`).
- **Пользовательское сообщение** передаёт данные товара как JSON и явно перечисляет
  отсутствующие поля, повторно запрещая их додумывать.
- Список характеристик намеренно **не** доверяется модели — он строится в коде, поэтому
  в промпте модель отвечает только за текстовую часть (описание, запросы, блок менеджера).

## Ограничения и возможные улучшения

Ограничения прототипа:

- Нет хранилища/истории — каждый запрос обрабатывается независимо (по ТЗ не требуется).
- Пост-проверка на выдуманные числа — **эвристика**: ловит значения с единицами и
  типоразмеры, но не семантические неточности (например, неверно названное назначение).
  Финальная вычитка человеком остаётся обязательной.
- «Базовый набор» характеристик для пометки «данных нет» общий, не привязан к типу
  прибора (манометр/термометр/датчик).
- Веб-форма — минимальная (без аутентификации, одиночный товар за раз).

Возможные улучшения:

- Пер-типовые шаблоны характеристик (для манометра ожидаем диапазон/класс точности/
  присоединение и т.д.) — точнее подсказывать, чего не хватает.
- Пакетная обработка и выгрузка (CSV/XLSX) для загрузки каталога.
- Строгий structured-output/JSON-schema на стороне API, где модель его поддерживает.
- Юнит-тесты на валидацию, factcheck и парсинг ответа; оффлайн-режим с моками.
- Контроль стоимости/логирование токенов и кэширование повторов.
